# 米家兑换码哨兵 · mihoyo-code-watch

盯着米游社、社区和 TapTap 活动中心里的**新兑换码 / 新福利活动**，一发现就推到你微信。
解决的是"知道我该领，但我不知道什么时候发了"。

**这个工程不碰你的游戏账号**：不登录、不签到、不自动兑换，只做"发现 + 提醒"。
所以它没有封号风险，也不需要把 Cookie 交出来（微博源除外，且默认关闭）。

推送分三类：

- **兑换码**：直接给出码本身（来自米游社搜索 / hoyo-codes）
- **福利活动**：给出活动页链接 + 截止时间 + 剩余库存（来自 TapTap 活动中心）
- **签到提醒**：累计签到型活动在活动期间**每天提醒一次**，带一键自动签到链接

---

## 为什么只做"提醒"而不是"自动领取"

这是刻意的选择，理由有三个：

1. **国服兑换码只能在游戏内兑换**。米哈游国服没有开放网页兑换接口（国际服走 HoYoLAB 有接口），
   所谓"自动兑换"在国服只能模拟 App / 游戏内 UI 操作，风控和维护成本高得离谱。
2. **自动化的合规风险正在变高**。曾经最流行的米游社自动签到项目
   `Womsxd/AutoMihoyoBBS` **已经被 GitHub 以违反服务条款停用**，只剩镜像和 fork。
3. **提醒的信息价值几乎等于自动领取**。兑换码的有效期通常是几小时到几天，
   收到推送后你自己花 10 秒在游戏里输入，结果完全一样，但风险归零。

---

## 整体方案：两条线分开处理

米哈游的"福利"其实是两类东西，成熟度差一个数量级，别混着解决。

| | 每日签到线 | 兑换码线（本工程） |
|---|---|---|
| **内容** | 游戏内签到、米游币任务、云游戏时长、米游币商城抢兑 | 微博超话、B站/抖音/小红书官号、版本前瞻直播码 |
| **特点** | 天天有，漏一天损失小 | 不定期、时效短，漏了就真没了 |
| **怎么办** | 用现成项目，别自己写 | 用本工程监控 + 推送 |

### 签到线：直接用现成项目

- **`Womsxd/MihoyoBBSTools`** —— 老牌，支持国服 + 国际服的原神/星铁/绝区零/崩坏3/崩坏2/未定事件簿，
  覆盖签到、米游币任务、云游戏、网页活动。支持 Docker / 青龙 / Nix / 云函数。
  ⚠️ 官方**明确不支持 GitHub Actions**（fork 会消耗上游额度导致仓库被封），别这么用。
- **`Akinome/miyoqian`（米游签）** —— 2026 年的新项目，有 Web 控制台、米游社 App 扫码登录、
  米游币商城定时/实时抢兑，**官方支持 GitHub Actions**（必须用 `Use this template`，不要 fork）。

既然你选了"GitHub Actions 免服务器"，签到线请用米游签，按它 README 的 Actions 章节走：
本地扫码登录一次拿到 `config.yaml` 和 `data/credentials.yaml`，两个文件内容分别塞进
仓库 Secrets 的 `MIYOUQIAN_CONFIG` / `MIYOUQIAN_CREDENTIALS`，然后手动跑一次 workflow 验证。

## 本工程：快速开始（GitHub Actions）

### 1. 建仓库

```bash
git init mihoyo-code-watch && cd mihoyo-code-watch
# 把本目录内容拷进来
git add . && git commit -m "init" && git push
```

建议用**公开仓库**：Actions 分钟数不限量，且 Secrets 在公开仓库里同样是加密的、日志里会自动打码。
（私有仓库每月只有 2000 分钟，本工程每 30 分钟跑一轮，容易吃满。）

### 2. 配推送通道

默认 PushPlus：微信扫码登录 <https://www.pushplus.plus>，复制 token。

在仓库 `Settings → Secrets and variables → Actions` 新建 Secret：

| Secret 名 | 用途 |
|---|---|
| `PUSHPLUS_TOKEN` | PushPlus token（默认通道） |

想换通道就再建一个变量 `NOTIFY_CHANNEL`，可选
`pushplus` / `serverchan` / `wecom`（企业微信机器人）/ `bark` / `telegram` / `none`，
并配上对应的 `SERVERCHAN_SENDKEY`、`WECOM_WEBHOOK`、`BARK_URL`、
`TELEGRAM_BOT_TOKEN` + `TELEGRAM_CHAT_ID`。

> 环境变量优先级高于 `config.json`，所以仓库里不用放任何密钥。

还有两个**可选**的 Secret，不配也完全能用：

| Secret 名 | 用途 | 代价 |
|---|---|---|
| `TAPTAP_COOKIE` | 让签到提醒显示「今日已签/累计几天」 | Cookie 等价于账号密码 |
| `WEIBO_COOKIE` | 启用微博源（默认关闭） | 同上 |

### 3. 手动跑一次

`Actions → 兑换码哨兵 → Run workflow`，勾上 `dry_run` 先看看抓到什么，确认没问题再放开。

**首次运行只登记不推送**（`first_run: "seed"`），否则第一次会一口气给你推几十个历史码。

### 4. 之后就不用管了

每 30 分钟跑一轮（`7,37 * * * *`，UTC）。发现新码 → 推微信 → 状态落盘并提交回仓库。
没有变化时**不会**产生提交，仓库不会被无意义 commit 刷屏。

## 本地运行

零第三方依赖，Python 3.8+ 直接跑：

```bash
cp config.example.json config.json     # Windows: copy config.example.json config.json
python run.py --dry-run                # 只抓取识别，不推送不写状态
python run.py                          # 正常跑一轮
python run.py --reset                  # 清空已推送记录，从头再来
python run.py -v                       # 调试日志
```

排查建议：先 `--dry-run -v`，看每个数据源返回了多少条、识别出哪些码。

### 怎么调阈值

识别兑换码靠启发式评分，不是正则一把梭。每个候选码的得分来自：
形态符合（+1）、附近有"兑换码/礼包码/前瞻"等词（+2）、命中已知前缀（+2）、
字母数字混合（+1）、长度在 10-16 之间（+1）。

`min_score` 默认 4。**如果你发现推送里出现明显不是码的英文单词，把它加到
`watcher/extractor.py` 的 `STOPWORDS` 里**，比调阈值更精准。

## 渠道签到：哪些能做、哪些做不了

很多人把「签到」和「领兑换码」当成一回事，其实是两条不同的链路。
**而且 TapTap 的签到奖励本身也分两类，这点曾经被我搞混过，这里写清楚：**

| 活动类型 | 发起方 | 签到给什么 |
|---|---|---|
| **TapTap 平台签到** | TapTap 自己 | 站内奖励：点券、红包、云玩会员卡、头像框（`app_title` = "TapTap"） |
| **游戏专项签到** | 游戏厂商 | 游戏礼包码 / 游戏内道具，部分活动明确写"发 15 位兑换码" |

所以「TapTap 签到必给兑换码」是**不成立**的。判断依据看活动详情里的 `reward.content`：
写"礼包码/CDKey/兑换码"的才发码，写"红包/点券/头像框"的就是站内奖励。
**实测校正**：绝区零 2026-09 那个「签到领好礼」给的是菲林（游戏内货币）+ 实物周边，
不含兑换码。别默认"签了就有码"。

| 渠道 | 能不能自动发现 | 能不能自动签到 | 本工程怎么做 |
|---|---|---|---|
| **TapTap 签到活动** | ✅ 完全能，匿名 | ⚠️ 接口已摸清，但**必须要登录态**，本工程不做 | 两个入口都扫（活动中心 + 各游戏活动页），自动发现 + **每日提醒** + 一键签到链接 |
| 好游快爆 | ⚠️ 需 Cookie | ⚠️ 需 Cookie | 未接入 |
| 小黑盒 | ⚠️ 需 Cookie | ⚠️ 需 Cookie | 未接入 |
| 微博超话 | ❌ 无 Cookie 直接被访客系统拦 | ❌ 需 Cookie + 多半要无头浏览器 | 未接入（见下节） |

### TapTap 签到接口摸底（2026-09 实测，从活动页 app.js 里挖出，非猜测）

这些端点是**真实存在**的，直接写在这里，省得你再去抓包：

| 用途 | 端点 | 匿名可用？ |
|---|---|---|
| 签到动作 | `POST /webapiv2/event/game-sign/check_in?activity_code={slug}` | ❌ 需登录态 |
| 签到状态 | `GET /webapiv2/event/game-sign/dynamic_data/{slug}` | ⚠️ 能调通，但"我"的字段全是默认值 |
| 领累计奖励 | `POST /webapiv2/event/game-sign/check_in_accept_award` | ❌ 需登录态 |
| 我的奖励 | `GET /webapiv2/event/game-sign/get_my_award_list/{slug}` | ❌ 需登录态 |
| 活动详情 | `GET /webapiv2/event/game-sign/detail/{slug}` | ✅ 完全可用（本工程在用） |

三个关键细节，都是踩出来的：

1. **参数必须放 query，不是 body**。`activity_code` 放 body 里会返回
   「「ActivityCode」必填」——同名的参数放 query 才被识别。
2. **还有一层防重放校验**。带上正确参数后，无登录态返回的是
   「网页已过期, 请刷新后重试!」，说明接口在签名/时间戳层面也设了卡。
3. **鉴权走 Cookie**（app.js 里没有 `X-Tap-Token` / `Authorization` 注入），
   `/webapiv2/account-profile/v1/me` 未登录返回 401 也印证了这点。

### 一个实测出来的捷径：`?auto_checkin=true`

活动页 URL 支持 `auto_checkin` 参数。app.js 里的 `triggerAutoCheckin()` 检测到它为 `true` 时，
会在**已登录状态**下自动调用签到（重试 3 次、每次间隔 1 秒）。

也就是说 —— **你浏览器里已经登录 TapTap 的话，点开带这个参数的链接就等于签到完成**，
不需要装任何东西，也不需要交出 Cookie。本工程的每日提醒直接给你这个链接。

> 注意：这一条是从页面代码里读出来的机制，**没有实际跑通过完整签到**
> （需要真实登录态 + 进行中的活动）。如果它在你那边不生效，退回手动点「立即签到」即可，
> 活动页网页版是支持签到的 —— 官方活动说明原文写着「在本页面点击『立即签到』」。

### 为什么本工程还是不替你签

1. **要交 Cookie**。上面所有签到端点都要求登录态，而 Cookie 等价于账号密码。
   本工程从第一天起就在回避这件事，不想为了省你 5 秒而破例。
2. **提醒的信息价值几乎等于自动签到**。每日提醒 + 一键链接，你点一下的成本是 2 秒。
3. **风控代价是真实的**。第三方自动化脚本被平台处置的案例存在，收益和风险的比值不划算。

### TapTap 源是怎么工作的

TapTap 这块要扫**两个地方**，缺一不可 —— 这是本工程踩过的最大的一个坑：

| 链路 | 扫什么 | 里面有什么 |
|---|---|---|
| **活动中心** | `/events` 全量 24 页 / 472 条 | 全站精选活动（下载有礼、抽奖、联动） |
| **游戏活动页** | `/app/{id}/game-event` | **该游戏自己的签到 / 礼包活动** |

**米哈游游戏的签到活动一条都不在活动中心里。** 实测（2026-09-12）：全量扫描
活动中心 472 条，`game-sign` 类型只有 3 条，没有一条属于米哈游；
而绝区零那个「签到领好礼」（9.3 万人参加、正在活动中）只挂在
`/app/234493/game-event`。早期版本只扫活动中心，等于**整个漏掉了米哈游的签到活动**。

所以配置里的 `taptap.apps` 不是可选项：

```json
"apps": {
  "原神": 168332,
  "崩坏：星穹铁道": 224267,
  "绝区零": 234493,
  "崩坏3": 10056,
  "未定事件簿": 172095,
  "崩坏学园2": 7158
}
```

app_id 从 `https://www.taptap.cn/app/<数字>` 地址里取；厂商页
`/developer/3103` 能一次列出米哈游旗下全部游戏。游戏活动页里每条活动带
`label_type`，据此判断性质：

| `label_type` | 是什么 | 默认推？ |
|---|---|---|
| `check_in` | 签到 | ✅ 并走「每日提醒」链路 |
| `gift` | 礼包，点击即领 | ✅ |
| `activity` | 创作征集（现金 / 周边） | ❌ 噪音大 |
| `lottery` | 抽奖 | ❌ |
| `in_app_event` | 游戏内活动 | ❌ |

想多推几类就往 `taptap.event_types` 里加。注意这些活动对象**没有稳定 id 字段**，
所以去重键（`post_id`）是用 `app_id + web_url` 派生出来的；另外它们的
`web_url` 有时是空串（例如星铁的新版本礼包只在客户端内领），这时退回用 title 做键。

`taptap.max_pages` 默认 24（全量 472 条），列表按发布时间倒序。活动中心里
签到类活动很少且不一定排在前面，所以默认全量扫（约 21 秒）。嫌请求多可以调小，
代价是可能漏掉靠后的活动。游戏活动页只多 6 个请求，开销可以忽略。

推送里会带上「剩余库存」（`剩余 1801/2000`），TapTap 的签到礼包是
**先到先得**的，看到库存不多了就尽快去领。已结束的活动会被识别并跳过
（列表页的 `expire_time` 经常是空的，光靠它滤不掉死活动，所以用详情接口的 `status_desc` 兜底）。

### 签到活动为什么要「每天提醒」

累计签到型活动的奖励按天数发（「累计签到 5 天领头像框」），**中间断一天就白费**。
一次性公告解决不了这个问题 —— 你看到公告的第 3 天就忘了。

所以 `sign_slug` 非空的活动额外走一条「每日提醒」链路：

- 活动进行期间，每轮运行都检查一次，**一天最多提醒一次**（按 `(slug, 日期)` 去重）
- 提醒里直接给 `?auto_checkin=true` 链接，点一下就签（见上一节）
- 同一天里，一个活动不会既出现在「新活动公告」又出现在「每日提醒」里
- 首次运行只登记不推送（和其他条目一致），不会上线当天就轰炸你
- 关掉这个行为：`taptap.daily_reminder: false`

**可选增强**：填了 `taptap.cookie` 之后，提醒里会多一行「累计签到 3 天，今日未签」——
这样连「签没签」都不用你自己回忆。不填也完全能用，只是推送变成纯提醒。

> 这个 Cookie 是 TapTap 网页版的登录态，等价于账号密码。
> **建议走 `TAPTAP_COOKIE` 环境变量**，并且只在你清楚代价的前提下开。
> 本工程把它做成可选项而不是默认需求，就是为了让你有得选。

⚠️ **签到活动是季节性的**——不少游戏只在版本节点前后开一两周。
**实测当前一个在线的签到活动都没有**（3 个都是往期），所以刚部署时你大概只收到抽奖/礼包类活动。
这不是坏了。

## 数据源：哪些能用，哪些不能

以下结论都是在本机实测过的（2026-09）。

| 数据源 | 状态 | 说明 |
|---|---|---|
| **米游社搜索** `bbs-api.miyoushe.com/post/wapi/searchPosts` | ✅ 可用 | 无需登录，**直接返回帖子正文**，兑换码就在正文里。本工程主力 |
| **hoyo-codes** `hoyo-codes.seria.moe` | ✅ 可用 | 公开 API，已验证的**国际服**码 |
| **TapTap 活动中心** `www.taptap.cn/events` | ✅ 可用 | 472 个活动匿名可读，含签到/礼包类。见下文「渠道签到」一节 |
| **TapTap 签到活动详情** `/webapiv2/event/game-sign/detail/{slug}` | ✅ 可用 | 匿名拿到每日奖励 + **剩余库存**。注意所有 webapiv2 接口都要带 `X-UA` query 参数 |
| **TapTap 签到动态数据** `/webapiv2/event/game-sign/dynamic_data/{slug}` | ⚠️ 需 Cookie | 「今天签没签」只在这里。匿名能调通，但 `disabled` 恒为 true，不可采信 |
| **TapTap 签到动作** `POST /webapiv2/event/game-sign/check_in?activity_code=` | ⚠️ 需 Cookie | 端点真实存在，但需登录态 + 过防重放校验。本工程**不调用**，见「渠道签到」一节 |
| 米游社版块列表 `getForumPostList` | ⚠️ 部分可用 | 只给标题和短摘要，拿不到正文，价值有限 |
| 米游社 `getPostFull` | ❌ 不可用 | 无登录态返回"请升级版本查看" |
| **微博** `m.weibo.cn` | ❌ 需 Cookie | 不带登录态直接 432 风控 |
| **B站** `api.bilibili.com` 动态接口 | ❌ 不可用 | 返回 `-352`，需要 wbi 签名 + 有效 buvid3，维护成本高，本工程没做 |

### 已知限制（请务必读完）

1. **米游社搜索是按相关度排序，不是按时间倒序**，单次最多 10 条，拿不到严格的时间线。
   所以本工程用 `fresh_hours` 做新鲜度闸门，而不是靠翻页。
   前瞻直播码这种高热度内容，通常几分钟内就会出现在"兑换码"关键词的前排，实用性没问题，
   但它**不是**一个完备的抓取器 —— 冷门活动码可能漏掉。
2. **国服/国际服要自己看**。推送里会尽量标注区域（靠正文里的"国服/国际服"就近归位），
   但社区帖子写法五花八门，标不出来的时候会写"未标注区域"。
3. **码有有效期**。推送时无法可靠判断是否过期，请以原帖说明为准。
4. **GitHub Actions 的 runner 在海外**，访问米游社接口偶发慢或超时。
   代码里已经做了重试和多源降级：单源失败只记警告，不影响其它源和状态落盘。
5. **游戏活动页只列"当前挂着"的活动，历史活动拿不到**。所以它只能告诉你
   「现在有什么」，不能给你一份往期清单。切活动时旧条目会直接消失。
6. **TapTap 的活动有时只在客户端可见**。例如星铁的「挥掷千星的筹码」礼包，
   网页端没有入口（`web_url` 是空的），本工程只能提醒你"去客户端领"。
   另外部分活动的签到按钮只在 App 内出现，网页端只有说明页。
7. **签到活动是季节性的**。全站 472 条活动里 `game-sign` 类常年只有个位数，
   米哈游这边更是"有活动才有"。某段时间一个签到活动都没有是**正常现象**，不是坏了。

## 合规与安全

- 本工程只读取**公开**的社区内容，不登录、不提交任何游戏操作，也不违反游戏用户协议。
- **`config.json` 已在 `.gitignore` 里**。如果你启用了微博源，`SUB` cookie 等价于账号密码，
  只能放 Secrets 或本地，绝不要提交、不要截图、不要发给任何人。

  用 `Use this template` 或者自己 `git init`。

## 想加数据源？

在 `watcher/sources/` 下新建模块，继承 `Source`：

```python
from . import Post, Source

class MySource(Source):
    name = "我的源"

    def __init__(self, cfg, now=None):
        ...

    def fetch(self):
        return [Post(source=self.name, title="...", text="含兑换码的正文",
                     url="...", game="原神")]
```

然后在 `watcher/sources/__init__.py` 的 `build_sources()` 里注册。
**数据源失败必须能降级**（抛异常即可，上层会捕获记警告），不要让一个源挂了拖垮整轮。

如果新源返回的是结构化字段而不是正文，用 `preset_codes=[(code, region, note)]`
直接给出码，绕过启发式识别 —— 否则奖励描述里的英文单词会被误判成兑换码
（这个坑已经踩过一次：`Mystic Enhancement Ore` → 假码 `ENHANCEMENT`）。

如果新源给的是「本身不带码、但要你知道」的情报（比如某个签到活动开了），
用 `announce=True` 并给一个稳定的 `post_id`。这类条目会跳过码提取、
按 `post_id` 去重后单独成段推送，参见 `taptap.py`。
